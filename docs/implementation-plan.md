- 日期：2026-10-02

- 规划讨论：[产品闭环与正式实施规划](https://ampcode.com/threads/T-01a0fab8-e6f1-71e8-934b-d7d421fca500)

## 1. 已确认的架构

| 项目 | 决策 |
| --- | --- |
| 产品形态 | 开源、本地部署，通过浏览器使用 |
| 用户体系 | 单用户实例，不做登录注册 |
| 前端 | React + Vite，保留现有组件、样式和交互 |
| 交付方式 | 开发时前后端分开运行；生产时一个 Node 服务提供界面和 API |
| Agent | `pi-agent-core + pi-ai`，应用内场景模块，不兼容 Pi Extensions |
| 学习代码 | 直接在本机执行，不使用容器；不具备沙箱隔离 |

### 1.1 实现技术建议

采用 pnpm workspace、TypeScript、Node 24 LTS、Hono、SQLite。SQLite 使用 `better-sqlite3`；真实终端采用 `node-pty`，浏览器端采用 `@xterm/xterm`。

Pi 采用已核实的新包名：

- `@earendil-works/pi-agent-core`
- `@earendil-works/pi-ai`

锁定同一 `1.0.0` 发布版本，完成兼容性验证后再接入业务，不浮动追踪 `latest`。M1 涉及的工程与兼容性验证技术已获批并验证，实际结果见 ROADMAP；浏览器终端与后续业务接入尚未实施。

### 1.2 Agent 框架的职责边界

- `pi-ai` 提供模型与 Provider 接入、统一消息及模型响应流。
- `pi-agent-core` 提供 Agent 状态、模型与工具调用循环、事件、中断、上下文转换和工具执行钩子。
- Core 的工具、钩子和事件不是完整插件系统；插件发现、加载和生命周期管理属于 `pi-coding-agent` 的 Extension 宿主能力。
- 当前三个第一方教学场景采用应用内模块组合，不为场景分化引入整个 `pi-coding-agent` 宿主。
- Core 的 `sessionId` 不等于产品级数据库会话管理。会话归属、持久化、恢复和并发控制由应用负责。

## 2. 正式目录及数据归属

```text
apps/
  web/src/
    app/                    # 入口、导航、布局
    features/               # 空间、需求、路线、课程、聊天
    components/ui/          # 通用组件
    lib/                    # API 与事件流客户端

  server/src/
    index.ts                # 服务启动与关闭
    http/                   # API、流式事件、终端连接、静态资源
    agents/
      runtime.ts            # Pi 装配、运行、中断与事件转换
      scenarios/
        intake.ts
        roadmap.ts
        tutor.ts
      tools/                # AgentTool 到业务操作的映射
    modules/
      spaces/
      sessions/
      learning/
      projects/
    storage/                # 数据库、迁移

packages/
  contracts/src/            # 请求、响应、业务产物与事件 schema
```

该目录树表达责任划分，不要求一开始生成全部空目录。

### 2.1 代码与状态边界

- 前端拥有界面状态，后端拥有业务状态；不把原型的全局内存 store 直接变成正式业务核心。
- `contracts` 只存放前后端真正共享的协议，不直接导出数据库模型或 Pi 的全部内部状态。
- Agent 只有服务端一个消费者，先放在服务端内部，不单独拆包。
- 不按教学场景拆服务，不创建万能 `shared` 包。
- 单元测试放在所属模块旁，跨前后端的验收测试单独组织。
- 字体等界面资源随应用分发，不依赖运行时在线加载。

### 2.2 用户数据

用户数据默认放在独立于源码的目录，例如：

```text
~/.teach-me-coding/
  app.db                    # 空间、会话、需求、路线、课件、测评
  projects/<space-id>/      # 项目文件的真实内容
```

支持通过启动配置调整数据目录。程序升级不得覆盖学习数据。

数据库不重复存储项目源码；编辑器和终端访问同一份磁盘文件。第一版使用应用管理的项目目录，不自动获得用户其他目录的文件访问入口。

## 3. Agent 运行与业务权限

三个场景共享运行层，分别定义教学指令、上下文、工具和产物 schema。

| 场景 | 上下文与职责 | 产物及应用方式 |
| --- | --- | --- |
| 前置提问 `intake` | 用户回答、已有需求草稿；整理目标、基础、成果和时间安排 | 需求草稿经用户确认后成为正式需求 |
| 学习路线 `roadmap` | 已确认需求、已有路线、相关能力证据；规划或提出调整 | 先形成路线提案，用户确认后由业务模块应用 |
| 课程辅导 `tutor` | 当前单元、相关学习结论、引用材料；讲解、练习与反馈 | 生成解释、练习反馈和学习结论，由业务模块校验和保存 |

课件生成、出题和评估作为明确的生成任务处理，不全部塞进同一个聊天历史，也不额外建设多 Agent 调度框架。

场景不等于会话。课程场景可以服务多个单元，但各单元保持独立 session；学习结论独立于聊天历史保存，场景间共享必要结论，不合并全部会话。

### 3.1 运行层保证

- 每个 session 同时最多一个运行，不在全局 Agent 上切换场景。
- 浏览器断线只结束订阅，不自动停止后台运行；用户点击停止才取消。
- 重连恢复已保存消息和运行状态，不重新提交同一次请求。
- 服务重启后将未完成运行标为中断，不自动重放文件修改或命令执行。
- 模型结构化产物经过校验；格式错误不能直接写入正式业务数据。
- 模型密钥只由服务端读取，不写入会话、不传回浏览器，也不传给终端子进程。

### 3.2 业务变更

Agent 产物不直接等于业务状态。以路线调整为例：

1. Agent 生成结构化提案。
2. 服务端校验并保存待确认提案。
3. 用户确认。
4. 业务模块校验并更新路线。

不让模型直接修改数据库，也不让前端从自然语言回答中猜测应执行的修改。

## 4. 本机执行的边界

**终端中的程序拥有启动服务用户的系统权限。工作目录限制不是安全隔离。**首次使用本机执行时必须明确说明。

首版采用以下规则：

- 服务默认只监听本机，不提供公开网络部署模式。
- HTTP 和终端连接校验允许的 Host、Origin，并使用请求令牌保护敏感操作；不开放任意跨域访问。
- 文件 API 检查路径和符号链接，拒绝越过项目根目录。
- 用户在终端主动输入的命令直接执行，不重复弹确认。
- Agent 主动修改文件或执行命令时，先展示修改内容或命令、目录，由用户确认。
- 不自动安装工具链、依赖或请求管理员权限；缺少 Rust、Python 等环境时给出准确指引。
- 应用关闭时清理自己创建的终端和运行进程。
- 取消操作不宣称能撤销已经发生的文件或系统修改。

这些措施减少误操作和接口滥用，不能把本机执行变成沙箱。没有登录注册也不意味着本地接口可以不做访问保护。

## 5. 按可验证阶段实施

| 阶段 | 工作与交付 | 验收重点 |
| --- | --- | --- |
| 1. 工程骨架与兼容性验证 | 在独立实施分支建立 workspace，验证 Pi、SQLite、PTY 与 Node 版本组合 | 单命令启动、静态页面/API、模型流式调用与取消、数据库读写、PTY 创建与退出 |
| 2. 原型迁移 | 将界面迁移到 Vite，保留交互；模拟数据暂作开发夹具 | 首页、会话隔离、目录树、普通／全屏 IDE、测评页面无回归；截图对照检查 |
| 3. 持久化与接口 | 将业务状态迁到后端，接入真实项目文件 | 刷新和重启恢复；多层文件操作；保存失败提示；外部文件变更不被静默覆盖 |
| 4. 三个 Agent 场景 | 用真实模型替换脚本回复，接入需求、路线、课程主流程 | 上下文不串会话；提案必须确认；非法产物被拒绝；中断与重试不重复写入 |
| 5. 真实终端与执行 | 替换模拟连接和运行器，接入本机终端及执行确认 | 文件与执行结果一致；中断、退出、缺工具链和权限失败可恢复 |
| 6. 整体交付验证 | 清理正式入口中的原型控制与硬编码回复，补充启动、配置和数据备份说明 | 生产模式单服务运行；完整学习主流程；升级不覆盖用户数据 |

保留现有 `prototype` 分支和 `.worktrees/prototype` 工作树作为参考，不直接覆盖。正式工程在基于主分支的独立实施分支中建设。

迁移阶段与行为替换分开验证，避免同时改变框架和业务后无法定位回归。

## 6. 风险、验证与范围限制

### 6.1 重点验证

- 会话隔离，包括不同空间、路线、不同单元及测评上下文。
- 重复提交、路线确认与有副作用操作的重复执行保护。
- 路径穿越、符号链接越界和本地接口访问保护。
- 断线重连、服务重启、运行取消及终端进程清理。
- 文件保存失败、外部文件修改与覆盖冲突。
- 页面、文件树、全屏切换及测评等代表性状态的浏览器检查和截图检查。
- 使用独立数据目录验证持久化和迁移，避免修改已有非测试数据。

模型测试区分可重复的模拟响应测试与真实 Provider 冒烟测试，不能用前者代替后者。

### 6.2 工程风险与验证限制

- Pi 新版本 API 和原生依赖安装是主要工程风险，放在第一阶段验证。
- `node-pty` 等原生依赖可能需要对应平台的编译工具，不能承诺所有机器均无需额外安装条件。
- 当前可直接验证的是开发机器上的 macOS；其他平台未经实际验证不宣称支持。
- 本文件中的检查描述验收计划，不代表测试已经执行或通过；实际实施与验证状态记录在 ROADMAP。

### 6.3 非目标

本轮不包含：

- 多用户、注册登录、角色权限。
- 容器执行环境或本机代码沙箱。
- 第三方插件加载及 Pi Extension 兼容。
- 自动部署、推送或发布。
- 未单独确认的产品增强，例如补救任务系统和最终作品验收。

上述产品增强可以在正式工程稳定后逐项设计接入。
