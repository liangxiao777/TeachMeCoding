## 1. 目标和已确认决策

需求确认要帮助用户明确想学什么、最终想完成什么，并核实会影响路线的技术事实。先增强现有 intake agent，不引入 multi-agent 编排平台。现有提示词已经要求动态追问，当前缺口是固定的界面建议、缺少独立的问题和回答记录，以及调研资料未可靠地交给下游生成。

- 关键技术事实未核实，agent 应先通过提问解决，不允许带免责声明的猜测路线；内容是否充分由 agent 判断，不用证据格式或逐字匹配代替判断。
- SQLite 是需求、问题、答案和调研资料的唯一权威存储；调研正文直接保存为 Markdown，查看、导出和下游上下文使用同一份正文。
- 需求采用可编辑表格，每行只有 `question` 和 `answer`；问题名称、数量和顺序由实际对话决定，不设置固定字段、技术分类或单独的版本对象。整张表格关联一份调研文档。
- 用户仍须显式确认需求，模型不能替用户确认。
- 保留主动停止、完整成功会话历史，以及不设应用 token/请求次数/工具次数预算的约定。2026-10-10 移除整轮 300 秒期限，改按 Pi 执行策略处理模型请求超时、瞬时错误退避与截断工具反馈；失败尝试只留诊断、不进入模型投影，具体契约见 [Agent 上下文约定第 4 节](./agent-context-design.md#4-一次运行及每次请求的契约)。Pi `streamSimple` 自身的输出上限策略未变。

## 2. 对话和核验行为

目标模糊时先问想完成什么，不先替用户选框架。技术名称有歧义时先确认对象；对新框架或版本敏感的功能，优先核验官方文档和发布说明。仅研究影响路线的技术身份、适用版本、必要基础和限制，不提前研究整个生态或生成完整教材。

用户未指定版本时，可推荐核验过的稳定版本，但必须在需求卡片展示并随需求确认，不能静默使用不断变化的“最新版”。概念类学习目标不强迫指定框架或版本。每轮通常问一两个会影响路线的问题，不重复询问已回答的内容。用户自述基础不等于测评证明的掌握程度；非关键字段可以留空。

搜索未配置时仍可抓取已知或用户提供的文档。必要资料仍缺失时，说明缺口并请求材料，不编造核验结论。

## 3. 数据和工具

### 需求状态

模型只提交 `{ rows: [{ question, answer }] }`。问题非空，回答是字符串，可以暂时留空；可自由合并、补充、重排问题，不要求逐字符对应提问原文。技术身份、版本、范围在必要时自然写进问答或 Markdown，不重复维护结构化目标对象。

宿主用现有需求修订号管理整表，用内部 `researchRef` 关联文档，不要求模型填写行 ID、资料 ID 或来源 ID。程序只检查基本数据结构、至少一行已有回答、待回答问题、用户确认和资料归属；不依赖固定字段判断内容完整性，也不强制所有技术目标必须先有调研文档。需要调研或仍有业务缺口时，由 agent 判断、记录和追问。

### 问题轮次

保存问题原文、选项、单选/多选方式、空间和会话归属、生成基线与回答。ID 由宿主生成。轮次状态为待回答、已回答或已取代。客户端提交稳定的问题/选项 ID 及真实自定义文本，服务端依据已存原始问题验证，不相信客户端标签。

每轮界面只显示一个问题。多个问题通过“上一个 / 下一个”切换，并显示“问题 n / 总数”；单个问题不显示切换栏。选项与自定义文本按问题 ID 保留，切换不提交、不清空回答，全部完成后统一提交。自定义输入标签为“填写自定义回答”，与输入框保留独立间距。已回答或已取代的历史问答也逐个浏览。切换使用普通按钮，不接管文本输入或单选控件的左右方向键。

`ask_user_question` 暂存问题；当前运行正常结束后才正式发布。用户回答开启下一次运行，不让一个原生工具调用长期挂起，也不新增运行层 waiting 状态。接受答案、记录用户消息、建立后续运行原子且幂等。模型回复失败不丢失已接受答案，重试不重复接受答案或清空新草稿。

用户直接发送新需求或修改摘要后，旧问题标为已取代。若同一轮同时提交草稿和问题，问题绑定提交后的需求版本，另保留生成时基线。

### 调研资料

`write_research_document` 只接收一个参数：`{ content: string }`。内容是完整 Markdown 文档，不要求路径、资料 ID、来源 ID、证据数组、固定标题或逐字摘录。同轮后一次写入替换暂存正文，正常结束后才形成一个固定版本；取消、截断、需求基线改变或后续发布失败时不留下半成品。

工具说明和 intake 提示词指导模型说明技术身份、适用版本、学习范围、必要基础及重要限制，区分事实、建议和未解决的问题，并用普通 Markdown 链接标注相关来源。允许用自己的语言整理材料。宿主只验证正文为非空字符串，原样保存换行、空白与代码缩进，不通过连续原文匹配、来源登记表或机械的内容清单拒绝文档。

宿主内部保留空间、run、ID、修订号、时间和 hash，以支持事务与下游固定版本引用，不要求模型维护这些信息。文档关联整张需求表格；同轮工具先后顺序不影响关联，也可以只更新资料。修改问答默认保留文档关联，不以文本相等判断相容性。agent 判断资料是否仍支持需求，实质变化时补充调研并更新文档；每次修改均需用户重新确认。

搜索和抓取的来源诊断仍进入运行 manifest，但不再生成供模型填写的来源 ID 或校验收据。诊断不证明文档结论正确，模型仍需判断来源与结论的关系。原始工具正文沿用既有省略策略，不额外持久化完整网页。

这是当前学习空间的正文写入工具，不开放通用文件系统 write/edit/bash，不增加双写文件。`submit_requirement_draft` 只提交完整的问题 / 回答表格，不能确认需求。前端支持修改两列、添加与移除行；用既有 Markdown 渲染器查看文档，导出直接返回保存的正文。原始 HTML 不执行，外部图片不自动加载，不启用危险或内网来源链接。

## 4. 上下文和所有权

新增的实际责任分别放在：

- `packages/contracts/src/intake.ts`：问题、回答和调研资料的共享契约。
- `packages/contracts/src/workspace.ts`：问题 / 回答表格契约。
- `apps/server/src/modules/intake.ts`：归属、版本、短事务、待回答问题及基本准入。
- `apps/server/src/agents/intake-tools.ts`：本轮 intake 工具及暂存产物。

现有 scenarios 组合工具，tools 继续统一装配搜索、抓取与扩展。intake XML 增加技术核验、提问、Markdown 内容指引和停止条件；JSON schema 只约束接口参数，不代替内容判断。上下文编译器沿用转义的 `<source>`，资料节点的正文直接是 Markdown，ID、修订和 hash 留在宿主元数据中，不将整个资料存储对象作为正文注入。

路线读取完整的确认问答及整表所关联的固定资料版本，课件读取完整问答和对应路线的固定资料版本；不依赖固定问题名称或行序。不能自动把所有 intake 原文注入下游，也不能查询“最新资料”默默覆盖生成依据。仅修改时间安排不重新调研；修改技术、版本或实质调研范围时由 agent 重新判断资料是否适用。新资料不自动改旧路线和课件，路线调整仍走现有显式确认。

## 5. 实施顺序

1. 从本地 main 建立隔离 worktree 和实施分支，使用独立临时数据目录。当前热更新服务连接真实学习数据，开发不得触发其迁移或重启。
2. 添加共享契约和追加式存储迁移，实现问题与回答事务、版本化资料和归属检查。
3. 接入工具、来源诊断、冻结上下文和规划准入。确认、建立规划运行和路线提交入口使用一致检查，不能只禁用前端按钮。
4. 在现有 AppModel 和 onboarding 组件接入选项、自定义回答、自由文本、可编辑问答表格、整表文档和阻塞原因；移除固定的会话建议。
5. 执行确定性测试、浏览器交互和实际截图检查，再以少量真实模型案例检查提问质量和依据。真实数据迁移与服务切换另行授权。

旧空间保留历史路线、课件和记录，不伪造历史核验数据。迁移 11 一次性把旧四字段及目标对象的有效内容转为普通问答行，同时转换冻结的重试上下文；保留答案原文、确认状态、版本与资料关联。不增加运行时旧格式适配层，不自动升级或重生成历史内容。

## 6. 验收和风险

计划验证以下反例，不只检查流程是否完成：

- 同名技术或版本冲突由 agent 澄清，缺少必要依据应继续调研或提问；接口成功不代表事实正确。
- 搜索关闭但已知文档 URL 仍可核验；概念类目标不用被迫选择框架。
- 篡改选项、跨空间回答、过期问题、重复回答被拒绝；单选、多选和实际自定义文本均正确留存。
- 回答提交断线后幂等重试；模型失败后答案仍存在；取消、截断、重启和迟到结果不发布半成品。
- 同轮草稿与问题绑定正确的提交后版本；用户后续编辑不被覆盖。
- 任意问题名称、数量和顺序均可保存，非关键答案可留空；编辑问答不丢掉整表文档关联，新资料不替换旧路线依据。
- 外部材料和自由文本被转义并作为不可信数据；跨空间资料不能引用，文档不执行脚本或触发远程图片请求。来源链接和结论的真实性由 agent 核实，不能把接口校验当作真实性证明。
- 浏览器检查键盘、窄屏、待回答、自定义输入、阻塞和失败恢复，并实际查看代表性截图。

首版不增加向量数据库、通用文档平台、文件双写或独立调研 worker。只有真实运行表明研究干扰问答质量或出现隔离需求，才考虑拆出 worker，复用现有资料契约。

追加式迁移必须在一次性数据上验证，并保留旧内容。上线前备份真实数据；服务切换和共享数据迁移不在本次开发授权中。
