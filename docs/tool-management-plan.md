## 1. 目标与边界

将 `agents/runtime.ts` 中的工具聚合与声明投影抽出为 `agents/tools.ts`。沿用 Pi 原生 `AgentTool` 和 `Tool`，从同一集合生成执行工具、模型声明和来源清单，不建设工具注册平台。

本轮保持现有工具名称、参数、顺序、场景可用范围和确认规则。新增行为仅为名称冲突时拒绝请求模型，以及在请求 manifest 中记录最终工具清单。

不为六个场景分别创建工具集文件，不迁移现有工具实现，不新增插件协议、权限引擎、配置 API、数据库表或管理 UI。不修改 XML 提示词，不收紧文件读取、Skills 或 MCP 权限。

此前讨论的场景共享能力白名单不在本轮实施：当前 Skills 在 intake 中依赖 `read` 加载技能正文，直接禁用读取会破坏已有行为。后续若收紧场景能力，须先明确技能文档读取、项目读取和 MCP 工具的选择规则，再单独实施和验证。

## 2. 目录与职责

```text
apps/server/src/agents/
├── tools.ts          # 新增：统一装配、冲突检查、声明和来源清单
├── tools.test.ts     # 新增：装配模块测试
├── runtime.ts        # 接入装配结果，保留运行生命周期
├── runtime.test.ts   # 补充运行接入及失败边界测试
├── scenarios.ts      # 保留会话场景工厂、暂存状态与 commit
├── tasks.ts          # 保留独立任务工厂、暂存状态与 commit
├── route-tools.ts    # 保留路线草稿操作
└── read-tools.ts     # 保留文件只读工具
```

`extensions/` 继续拥有 MCP、搜索、网页读取和 Skills 的实现、配置及连接生命周期。`modules/` 继续拥有业务状态、版本校验和本机操作确认。Pi 继续负责参数校验、顺序调度、工具调用和错误结果，装配模块不直接调用工具的 `execute()`。

## 3. 装配契约

`prepareTools()` 接收场景工具、默认目录解析函数、是否需要 Skills 读取、MCP/搜索服务、网页工具配置和运行取消信号，返回：

```ts
type PreparedTools = {
  tools: AgentTool[];
  declarations: Tool[];
  inventory: Array<{
    name: string;
    source: 'scenario' | 'skills-read' | 'mcp' | 'search' | 'web-fetch';
  }>;
};
```

- 固定装配顺序：场景工具 → Skills 补充读取 → MCP → 搜索 → 网页读取。
- Skills 补充读取按名称避让已有场景工具，保留原场景工具的优先级。
- 默认目录通过 `cwd: () => string` 按需解析，在 MCP 获取完成且未取消之后，仅为 Skills 读取调用。`Projects.root()` 会创建目录，提前或无条件解析会增加文件系统副作用。
- 其余同名工具明确报错，指出名称及两个装配来源，不覆盖、不自动改名；不得启动模型请求或执行工具。
- 模型声明从同一工具集合投影，保留 `name`、`description`、`parameters` 和可选 `outputSchema`，不使用会丢失本项目字段的替代投影。
- 来源表示装配来源，而非权限或底层实现文件；例如 tutor 自带的 `read` 来源为 `scenario`。
- 外部服务获取接收运行取消信号，在等待前后检查取消；runtime 在装配完成后仍检查实际运行状态。
- 每个 run 装配一次，不建立全局可变注册表。工具清单固定不代表外部服务始终可用。

## 4. 保留现有场景与服务规则

| 场景 | 业务工具来源 |
| --- | --- |
| intake | 需求草稿工具 |
| roadmap | 路线阶段、单元构建与提交工具 |
| tutor | 文件读取、学习结论，以及接入 Actions 时的本机操作提案 |
| lesson | 课件提交工具 |
| assessment | 出题提交工具 |
| evaluation | 评估提交工具 |

业务集合仍由 `createScenario()` / `createTask()` 创建，装配模块不重复维护工具名列表。

所有场景继续按当前配置加入共享能力：有启用的 Skills 时补齐读取工具；加入已连接 MCP 服务的工具；搜索须启用且认证就绪；`web_fetch` 始终加入。

`runtime.ts` 继续拥有运行状态、取消、事件、顺序执行配置和正常结束后的 `commit()`。本机文件/命令工具仍只生成提案，用户确认后由 `Actions.decide()` 执行。MCP 不增加统一审批层。

搜索关闭仍中断正在进行的 Agent 搜索；配置更新不重绑定旧工具。MCP 重连或工具列表更新不自动替换当前 run 的工具。连接失败、认证缺失及取消继续遵循原服务处理方式。

## 5. 请求清单与兼容性

每次请求的现有 manifest 增加 `toolInventory`，只包含最终工具名称和装配来源，不存参数值、工具正文、认证字段或服务配置。

保留 `extensions.skills`、`extensions.mcpTools` 和实际调用产生的 `toolSources`。`mcpTools` 从同一 inventory 的 MCP 条目派生，避免另行维护名单。清单说明可用工具，`toolSources` 说明已调用工具的证据来源，二者不混用。

旧 manifest 原样保留，允许缺少新字段；不迁移或重写历史记录，也不改变业务和消息协议。

## 6. 实施步骤

1. **纯抽取并验证行为。** 新建装配模块，迁移聚合与声明投影，接入 runtime，先保持对外行为和 manifest 字段不变。验证六个场景和扩展开关组合的集合、顺序、schema 及调用生命周期。
2. **增加冲突检查与来源记录。** 加入名称唯一性检查，在现有 manifest 写入 `toolInventory`，补充失败及记录测试。
3. **回归与交付。** 执行针对性测试及 `pnpm build`、`pnpm check`、`pnpm test`，记录实际结果与限制。使用合成模型、假凭据和可丢弃数据，不调用收费模型，不操作用户学习数据，不启动生产服务。

## 7. 验收与风险

- 六个场景的业务工具正确，共享工具遵循当前配置，工具顺序保持不变。
- Skills 读取补齐不重复、不覆盖已有工具，当前 intake 技能加载行为保持可用。
- 两个同名但 schema/实现不同的工具被拒绝；模型、工具和 commit 均不调用。
- 执行工具、模型声明和 inventory 名称顺序一致，参数及 `outputSchema` 不丢失。
- 已取消、等待 MCP 或搜索时取消的装配不启动模型或晚提交。
- 当前 run 保留配置快照，搜索关闭和 MCP 重连不误切换执行对象。
- 新清单不含秘密或工具正文，原有实际调用来源及留存规则不变。
- 失败不破坏有效业务产物，既有场景提交、取消和私有测评展示边界保持不变。

回滚只需撤销本次源码与文档修改；没有数据库或配置迁移。历史 manifest 的可选新字段不参与业务状态，不需要清理用户数据。
